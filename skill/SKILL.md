# Riftbound Library

This library holds two independent books: **deckbuilding** (what to put in a deck, before the game starts) and **gameplay** (what to do with it, turn by turn, once the game is live). They are different skills that happen to share one game — a question about mulligan strategy is not a question about rune ratios, and blending them into one undifferentiated wall of advice makes both worse. Route to the one that fits, read it whole, then answer.

## Picking a book

1. `ls ${CLAUDE_SKILL_DIR}/references/` first — the book list is whatever's actually on disk, not a hardcoded list here. A written-out list in this file would be a second copy of the truth, and it would drift the moment a book is added or renamed. Use the full `${CLAUDE_SKILL_DIR}`-qualified path, not a bare relative one: this file's relative paths resolve against the current working directory Claude Code happens to be running in, not against wherever this skill folder itself is installed, so a bare `ls references/` silently fails whenever the two aren't the same directory. `${CLAUDE_SKILL_DIR}` is a Claude Code-provided substitution that always resolves to this file's own containing folder regardless of working directory — every relative path below is written the same way for the same reason.
2. A book lives at `${CLAUDE_SKILL_DIR}/references/<book>/<book>.md`. **Read the whole book before answering** — each one is designed as a self-contained routing table + methodology package, not a grab-bag of independent tips you can sample from.
3. Deckbuilding questions ("can I build X", "is this card/deck legal", "how should I split my runes", "write a theme-deck guide", "does this classic decklist still work after the ban update") → `deckbuilding` book.
4. Gameplay questions ("do I attack this battlefield or wait", "how do I mulligan this hand", "how should I think about this chain/priority decision", "how do I actually pilot this specific deck") → `gameplay` book, answered as strategic judgment grounded in mechanics — see "Boundary" below before answering a question about one *specific*, already-happened interaction.

## Boundary — strategy advisor, not a rules judge

Both books teach real Riftbound mechanics and can reason through how a rule *generally* works — that's what makes the strategic advice usable at all, not a scope violation. The line is about a different axis: **whose call is final.**

- **In scope, answer directly**: deck construction, archetype/matchup reasoning, mulligan calls, whether to initiate or hold a Showdown, how to sequence a turn, how to pilot a specific decklist (the gameplay book's deck-primer format), and explaining how a mechanic works in general (how the chain resolves, how damage is assigned, what a keyword does).
- **Out of scope, give background + defer**: a ruling on one specific, already-happened interaction that a Judge would need to settle (an ambiguous trigger-timing dispute, a tournament penalty question, "who's right, me or my opponent, about what just happened at the table"). For these: explain the relevant rule and give a most-likely read if one exists, state explicitly that it isn't a ruling, and point to `app.riftjudge.com` (community rulings database) or the event's actual Head Judge — never present a confident guess as if it settles the disagreement.
- **Signal words that should trigger the deferral, not a confident verdict**: "who's right," "is this legal to do right now," "what's the ruling," "the judge said X, is that correct," any question about a specific tournament penalty. These sound like gameplay questions but are actually asking this library to act as the authority of record, which it isn't — see `gameplay.md`'s "Process discipline" section for the same rule stated from that book's side.

## Route, don't snapshot — the one rule that governs both books

Riftbound's rules text and legal card pool are a live, Riot-maintained thing, not a fact this file already knows for all time. The official Rules Hub —

**https://playriftbound.com/en-us/rules-hub/**

— hosts the Core Rules PDF, the Tournament Rules PDF, the current ban lists (Constructed and 2v2 separately), and card errata, and Riot edits it directly when something changes (most recently the ban list moved 2026-07-24). That domain used to be `riftbound.leagueoflegends.com`; it now 301-redirects to `playriftbound.com` — if a citation or bookmark still points at the old host, follow the redirect rather than trusting a possibly-stale mirror.

- **Base rules** — turn phases, how the chain resolves, how combat is scored — are stable mechanics, not a moving target, so the books below summarize them directly and cite where they came from. That doesn't mean any one document is the top of the stack for every question — see the authority model below.
- **Two different questions need two different precedence orders — don't collapse them into one "the Core Rules PDF is the source" mental model.** An independent audit of this library (2026-08-17) found the previous version of this section did exactly that, and it's a real failure mode: it means the agent gets routed to a known-stale local snapshot at exactly the moment a fresher official source exists and actually matters.
  - **Competitive-procedure questions** (deck legality, tournament conduct, what a judge would rule) — 1) that specific event's own addendum, if one exists and applies, 2) the Tournament Rules PDF, 3) whatever the Core Rules cover that the Tournament Rules don't modify. Tournament Rules 104.1: where Tournament Rules conflict with or add to the Core Rules, Tournament Rules govern for competitive play. 104.3: an event's own addendum can further override the Tournament Rules. In an actual live event, Tournament Rules 204.4 makes the Head Judge the final authority on procedure — this library can inform a judge call, it can't make one.
  - **Game-mechanics and card-text questions** (what a card does, how an interaction resolves) — 1) a current official FAQ/clarification, within whatever scope it states, 2) the latest Core Rules, 3) card text with errata applied (the Core Rules' own Golden Rule: printed/corrected card text overrides a general rule it contradicts). A dated FAQ can outrank a newer-looking PDF: the 2026-08-14 Vendetta Rules FAQ explicitly states that where it differs from the Core Rules as they stood then, the FAQ governs — until the next Core Rules revision supersedes it. Check the FAQ's own stated date against this library's `last-verified` date before assuming the PDF alone is current enough.
- **Card data and the ban list should be read from a local file first for routine questions — but "local-first" is a starting point, not an excuse to skip freshness checks.** This library bundles its own `${CLAUDE_SKILL_DIR}/data/riftcodex_cards_raw.json` — full official English rules text for every card in OGN, OGS, SFD, UNL, and VEN (the currently-released Standard sets as of the last harvest), sourced from api.riftcodex.com (see `${CLAUDE_SKILL_DIR}/data/README.md` for provenance and known gaps — no RAD/Radiance yet as of the last harvest, and ARC/FND aren't in riftcodex's coverage at all) — so it travels automatically with this folder wherever it's copied or symlinked, no separate step needed. A deployment can override it with something more current or better-integrated via a private companion skill folder (commonly named with a `-private` suffix, see below) that binds specific local paths; check for one of those first, and fall back to this library's own bundled `data/` when none exists. Read whichever one applies fresh each time rather than trusting an answer from earlier in the conversation. Neither source has a ban-status field — bans are a separate, Riot-official axis, always cross-check the live Rules Hub or a private companion's ban-list binding for that.
- **A harvested dataset is not the same thing as a current one.** `riftcodex_cards_raw.json` is a snapshot from one point in time; Riot issues card errata after a set ships, and the raw file does not update itself. Before quoting any card's ability text as current, check `${CLAUDE_SKILL_DIR}/data/errata_overlay.json` for that card's `official_name` — if it has an entry, the overlay's `new_text` is the current wording, not whatever the raw file says. The raw file is deliberately left unedited (it stays a faithful mirror of what riftcodex.com actually returned) rather than patched in place, so the overlay is the correction layer, checked on every read, not a one-time fix. The overlay is itself a snapshot (`last_verified` date at its top) and not guaranteed complete for cards outside the four errata waves it currently tracks — if a card's behavior seems off despite no overlay entry, or enough time has passed since `last_verified` that a new errata wave is plausible, that's a reason to escalate to a live fetch of the Rules Hub's errata pages, not a reason to assume "no overlay entry" means "definitely current."
- **When source freshness genuinely matters for the question being asked, check it before answering, not after.** For a competitive-legality or tournament-procedure question, that means actually reading the applicable Tournament Rules section (not recalling it) before answering. For a card-interaction question that isn't obviously trivial, that means checking whether the Rules Hub's most recent FAQ postdates this library's local snapshot. For a routine "what does this card do," local data plus the errata overlay is genuinely sufficient and a live fetch would be wasted latency for no accuracy gain — the point isn't "always fetch," it's "let the question decide," not "local is the default no matter what's being asked."
- **Don't invent official wording that isn't actually available.** If verbatim official card text is needed in a language or form the local data doesn't have, say so plainly rather than translating/paraphrasing something else and presenting it as the official printed wording — then fetch a source that mirrors the actual print, or defer.
- **The same discipline that governs the deckbuilding book's card-pool sections applies whenever any book names a specific card or archetype**: a claim sourced from before Riftbound's first ban wave (2026-03-31) may describe something already banned everywhere, including in a region that hasn't even launched yet — see the deckbuilding book's `regional-legality-model.md` "compound gap" section for why. This is a library-wide rule, not a deckbuilding-only one; the gameplay book currently stays at the card-agnostic mechanics level specifically to avoid this exposure.
- Community sites — riftbound.gg, learnriftbound.gg, riftbound.zone, runesandrift.com, riftmana.com, app.riftjudge.com (a community-run rulings/FAQ database, useful for edge-case interaction questions) — are good for explanation and worked examples, but none of them are Riot. Cite them as community analysis, and defer to the official PDFs whenever the two disagree.

## Public library, private companion

Everything in this folder (`SKILL.md` and everything under `references/`) is written to be portable — no private repo paths, no one deployment's internal function/file names. That's deliberate: this folder's real canonical location is a separate, independent public repo, and any private repo that uses it reaches it via a local mirror (a directory junction on that machine, not a copy) rather than owning its own duplicate — edit the content once, it's correct everywhere it's used, nothing to keep in sync by hand.

The trade a private deployment makes for that portability: this folder can never name a specific repo's actual file paths, function names, or local database locations, even though real answers sometimes need them. The fix is a **sibling folder, not a mirrored one** — conventionally named with a `-private` suffix (e.g. `riftbound-private`, sitting next to this `riftbound` folder, never inside it) — that exists only in a given private deployment, is never part of what's mirrored publicly, and holds exactly the bindings this book intentionally left generic: which local file has the card database, which has the ban list, how a specific site's content-authoring conventions work. Check for it at a path built from `${CLAUDE_SKILL_DIR}` (its parent directory, then a `-private`-suffixed sibling of this folder's own name) rather than a bare relative guess, for the same working-directory reason as everywhere else in this file. If such a folder exists, read it whenever this book says "a private companion, if one exists" or "your local database." If it doesn't exist, there's no private deployment here — the generic instructions in this book are all there is, and that's fine for a project working directly off the datasets this library itself ships with.
